# 座標 → 運動指令 → TCP 串流 (Skill 3)

上游是 Skill 2(`sugar-points`)的座標 JSON。這一關決定**怎麼走**,然後送上機台。

手臂端不預先知道有幾個點,只跑一支常駐程式收字串。所有決策都在 PC 端。

## 為什麼「先收滿一整筆劃再動」

一問一答式的即時執行會變成 stop-and-go —— 傳一個點、等執行完、再傳下一個,
**每個往返停頓都是一坨糖**。

所以 `PT`/`AR` 只填手臂端的緩衝陣列,收到 `RUN` 才一次連續走完。
配合 Skill 1 的 `--link char`,一個字就是一筆,等於「傳一次執行一次」。

## 動作型態怎麼選

只用兩種插補:**直線(L)畫圖,關節(J)趕路**。

| 情況 | 指令 | 理由 |
|---|---|---|
| 筆劃內的每一段 | `LMOVE` | 直線插補,路徑完全可預測 |
| 移到下一筆起點的上方 | `LAPPRO`(預設) / `JAPPRO` | 見下方 |
| 下筆(從上方降到工件) | `LMOVE` | 必須垂直 |
| 抬筆(離開工件) | `LDEPART` | 沿噴嘴軸垂直退開 |

### 為什麼用 APPRO / DEPART 而不是自己算 zup

```
JAPPRO pose, dist   關節插補到「距 pose 沿工具 Z 退開 dist」的位置
LAPPRO pose, dist   同上但直線插補
LDEPART dist        從目前位置沿工具 Z 退開 dist
```

(AS 語言參考手冊 90209-1025DE p.6-5 / p.6-6。dist 為正 = 往工具 Z 負方向,
噴嘴朝下時就是「往上」。)

關鍵差別:這些指令沿的是**工具 Z 軸**,不是 base Z。自己寫
`LMOVE SHIFT(base BY x,y,zup)` 的話,只要工具沒有完全垂直於畫布,
退刀就會斜著走,可能刮到剛畫好的糖。`LDEPART` 保證沿噴嘴軸垂直退開。

### 空中移動(`--air-move`)預設用 LAPPRO

`JAPPRO` 是關節插補,通常比較快,而且空中移動的路徑本來就不重要。

**但關節插補的笛卡爾路徑不可預測,中途可能下沉。** 抬筆高度只有 15mm 時,
可能刮到剛畫好的糖。要用 `jmove` 就先把 `--zup` 拉高並實際跑過一次。

### 為什麼不用圓弧插補

Kawasaki 有圓弧,寫法是 `C1MOVE`(弧上中點)+ `C2MOVE`(終點),圓由
「前一動作的位置 + C1 點 + C2 點」決定(手冊 p.6-14)。理論上一段圓弧
兩道指令就能取代十幾個直線點。

**但圓弧段內速度不能變** —— C1 和 C2 之間沒有中間點可以下 `SPEED`,
而毛筆的粗細正是靠速度做的。毛筆開得越細膩,能用圓弧的地方越少。
這是本質衝突,不是實作問題。

實測過再決定放棄的,四個字的數據:

| 設定 | 指令數 | 封包數 |
|---|---|---|
| 只用 LMOVE | 373 | **40** |
| 加圓弧 | 313 (−16%) | 90 (+125%) |
| 加圓弧 + 量化放粗到 40 | 264 (−29%) | 105 (+163%) |

圓弧是拿封包數換指令數,而兩者都不是這個應用的瓶頸(瓶頸是抬筆和畫線本身
的時間)。少一種動作型態就少一條沒在實機驗證過的分支,所以拿掉了。

## 速度怎麼算

糖流量固定,所以**線寬 × 速度 = 常數**:

```
speed = clamp(draw_speed / width, draw_speed, max_speed)
```

`width` 是 Skill 2 傳下來的相對粗細(0.28~1.20)。量化到 `--speed-quant`
的倍數,只有變速時才下 `SPEED`,不然每個點都會冒一行。

**`--speed-quant` 必須跟 `svg2points.py` 用同一個值。** Skill 2 是靠它決定
「哪些點是速度換檔點、必須保留」,兩邊不一致的話那些點就白留了。

`--max-speed` 預設是畫線速度的 4 倍。**不要調超過 4 倍** —— 對比再大糖絲會斷,
而且真跡量到的粗細對比也只有 4 倍。

## 停留時間

| 時機 | 預設 | 作用 |
|---|---|---|
| 下筆後 | 0.15s | 等糖絲成形再走,不然開頭會斷 |
| 收筆後 | 0.10s | 等糖絲斷乾淨再抬筆,不然會拖絲 |
| 糖點 | `--dot-ms` × 直徑 | 要塗滿的地方停久一點,糖就多 |

前兩個寫在手臂端 `sugar_server.as` 的 `sub_run` 裡,要改直接改那支。

## 怎麼跑

```bash
PY=~/Documents/義大/.venv/bin/python
SA=~/Documents/義大/sugar_arm

# 先 dry-run 看封包,不連手臂
$PY $SA/stream.py points.json --dry-run --base 450,0,-120 --draw-speed 60

# 不接手臂測協定:一個終端機開假手臂,另一個送
$PY $SA/stream.py --fake-server --port 10123
$PY $SA/stream.py points.json --host 127.0.0.1 --port 10123

# 實際上機
$PY $SA/stream.py points.json --host 192.168.0.2 --base 450,0,-120 --draw-speed 60
```

**上機前一定要先跑 `--fake-server` 的迴路測試。** 那會驗證封包長度、
框架、以及所有指令都被接受。

## 通訊協定

```
BEG,<點數>              宣告一筆劃,清空緩衝
PT,x,y,v,x,y,v,...      直線點,每點帶速度
RUN                     一次連續走完緩衝區
DOT,x,y,秒              糖點
BASE,x,y,z,o,a,t        畫布原點
SPD,畫線,空走,精度
AIR,0|1                 空中移動 0=LAPPRO 1=JAPPRO
HOME / END
```

手臂每收一行回 `OK` 或 `ER`。

**兩邊都不加換行字元。** AS 的 `TCP_SEND` 是把字串陣列原樣送出,不會補 `\n`,
用 `readline()` 等換行會直接卡死。framing 靠「送一行就等回覆」保證每次
`TCP_RECV` 剛好拿到一整行。

單封包上限 250 字元(手冊限制 255,留餘裕)。

## 手臂端

`sugar_arm/arm/sugar_server.as` 載進控制器常駐執行。

前置需求:**Ethernet 選購板卡**。沒裝的話 TCPIP 指令直接報 E4054。

手冊查證過的限制:埠號 8192–65535、timeout 1–60 秒、每元素字元上限 1–255、
單次收發 ≤4096 bytes。

要改糖閥編號、抬筆高度、精度,直接改那支開頭的參數區。

## 上機檢查表

1. **TCP 校正做了嗎** — 工具座標要設在噴嘴尖端。沒設的話 `z=0` 會落在
   法蘭中心,差幾十到一百多 mm,會直接撞板
2. **`base` 三點校正了嗎** — `BASE,x,y,z,o,a,t` 的值要是實際量到的
3. **`--bead` 是實測值嗎** — 預設 2.5mm 是估的。它同時決定 Skill 2 的
   取樣容差,不準的話上游也跟著錯
4. **`--accuracy` 夠大嗎** — 預設 3mm。設太小(尤其設 0)控制器會逐點停,
   糖在每個點積一坨
5. **先空跑一次** — 糖閥不開,只走路徑,確認不會撞、不會超出行程

## 失敗樣態

| 症狀 | 原因 | 處置 |
|---|---|---|
| 連線卡住不動 | 兩邊 framing 不一致 | 確認都沒加換行 |
| 手臂回 `ER` | 指令字打錯或欄位數不對 | 看 `--dry-run` 印出的那行 |
| 「封包超過上限」 | 單點座標位數太多 | 正常不會發生,檢查座標是不是異常大 |
| 線寬忽粗忽細 | `--speed-quant` 跟 Skill 2 不一致 | 兩邊改成同一個值 |
| 每個點都停一下 | `--accuracy` 太小 | 調大到 3~5mm |
| 轉角積糖 | 同上,或該處速度太慢 | 調大 accuracy,或降低 `--curve-gain` |

## 交付時要講的三個數字

1. **指令數與封包數**
2. **速度範圍** — 60~240 mm/s,對比幾倍
3. **抬筆次數** — 這通常是總時間的一半以上,講出來才知道瓶頸在哪
